# ONOD Fonts — comprehensive product / UX / data / engineering audit

Date: 2026-08-10

Repository: `IMONsergey/onod-fonts`

Status: audit baseline for the next major update. `main` remains the single source of truth.

## Executive summary

ONOD Fonts already has a strong product shell: a distinctive typographic catalog, font detail laboratory, favorites, comparison workbench, an educational Protocol section, localization, persistent collections, and a working standalone GitHub Pages deployment.

The main problem is not visual polish. The main problem is that the interface currently communicates a level of typographic and licensing precision that the underlying data and loading infrastructure do not consistently provide.

The highest-priority gap is **trust**:

1. a significant portion of font metadata is synthesized heuristically rather than sourced from authoritative manifests;
2. the Google Fonts loading cache can silently reuse an unrelated previous batch after filtering or navigation;
3. multiple UI controls expose weights / variable behavior that may not correspond to assets actually loaded into the browser;
4. comparison sharing does not encode the compared font IDs, so a copied Workbench URL is not a portable comparison;
5. the current quality gate validates TypeScript + Vite build only — it does not validate catalog truth, font availability, routing, accessibility, or critical user workflows.

Until those layers are fixed, adding more fonts or more visual features increases the surface area of uncertainty.

## Severity model

- **P0 — product integrity:** can display materially wrong information or a fallback while presenting it as a real font.
- **P1 — major product / workflow defect:** core workflow is misleading, non-portable, inaccessible, or easy to lose.
- **P2 — significant quality gap:** weakens usability, performance, localization, SEO, maintainability, or mobile behavior.
- **P3 — polish / cleanup:** not immediately blocking but should be removed before treating the product as mature.

# P0 — product integrity defects

## P0.1 — font metadata is frequently generated, not authoritative

Primary file: `src/app/data/mockFonts.ts`

The `Font` interface looks authoritative, but a large portion of its records are assembled through `createFont()`, `genWeights()`, `guessCategory()`, and bulk dataset loops.

### Specific problems

`createFont()` currently defaults to:

- `license: "Open Source"`;
- generic generated descriptions;
- a generated source URL based on the family name;
- generated weight values from a requested *count*;
- one category provided by a heuristic source list;
- language support inferred from a manually curated whitelist / naming rules;
- styles reduced to `Regular` and optionally `Variable`.

`genWeights(count)` invents concrete CSS weights from a numeric count. A source saying "4 weights" cannot be converted safely into an arbitrary set of 100/300/500/700-style values.

`guessCategory(name)` infers classification from words in the font name. This is not a valid source of typographic classification.

There are also explicit bulk heuristics such as:

- `classicData`: `isVar = i % 10 === 0` and weight count depends on array index;
- every `fontshareData` entry is created with `8` weights and `variable=true`;
- every `googleMiscData` entry is created with `4` weights and `variable=true`;
- broad independent groups are assigned shared weight / variable assumptions.

These are acceptable for a mock prototype but not for a public catalog whose UI presents those values as facts.

### Impact

This affects:

- filters;
- sorting;
- footer statistics;
- weight selectors;
- variable-font badges;
- Cyrillic badges;
- pairing logic;
- source / license descriptions;
- CSS output;
- the perceived credibility of the entire product.

### Required fix

Replace generated semantic metadata with a canonical, provenance-aware dataset. Every fact that appears in the UI should carry a source and validation status.

Recommended minimum record model:

```ts
type FontRecord = {
  id: string;
  family: string;
  foundry?: string;
  designers?: string[];
  classification: FontClassification[];
  scripts: ScriptCoverage[];
  license: {
    id: string;
    label: string;
    url: string;
    commercialUse?: "yes" | "no" | "unknown";
    redistribution?: "yes" | "no" | "unknown";
  };
  source: {
    provider: string;
    specimenUrl: string;
    downloadUrl?: string;
    cssUrl?: string;
    repositoryUrl?: string;
  };
  faces: FontFaceRecord[];
  axes?: VariableAxisRecord[];
  provenance: {
    verifiedAt: string;
    verifiedBy: string;
    sourceUrls: string[];
    confidence: "verified" | "derived" | "unknown";
  };
};
```

Unknown values should be displayed as unknown, not guessed.

## P0.2 — Google font loader cache keys collide across unrelated font sets

Primary file: `src/app/components/FontLoader.tsx`

Google fonts are loaded in batches and the stylesheet ID is derived only from the batch offset:

```ts
addStylesheet(url, `gf-batch-${i}`)
```

`globalLoadedIds` persists across component instances and route changes.

### Failure scenario

1. Catalog loads first 15 Google fonts into `gf-batch-0`.
2. User filters the catalog to a completely different set.
3. `FontLoader` builds a new URL but again asks to add `gf-batch-0`.
4. `globalLoadedIds` says it is already loaded.
5. New stylesheet is skipped.
6. Cards render their `fontFamily`, but the browser may fall back to `serif`, `sans-serif`, or `monospace`.
7. UI provides no warning that the requested family never loaded.

The same collision can occur when navigating into a font details page, favorites, or Workbench.

### Impact

This is a core functional defect: the catalog may visually compare fallback fonts while looking successful.

### Required fix

Use deterministic content-addressed loader keys, for example a hash of normalized family + requested faces / axes. Better: manage loading at the individual family/face level with a central registry.

The UI should also expose `loading / ready / failed` state per family.

## P0.3 — rendered weights do not reliably match loaded font files

Files:

- `src/app/components/FontLoader.tsx`
- `src/app/components/FontCard.tsx`
- `src/app/pages/FontDetailsPage.tsx`

For non-variable Google fonts the loader currently requests the family without explicit weights. The UI can then expose multiple weights from `font.weights`, while the browser may only have the default face and synthesize the rest.

For variable entries the loader assumes `wght@100..900`, even though variable axes and ranges are not stored authoritatively.

`customCssUrl` assets can likewise expose only a subset of the weights claimed by the catalog.

`FontCard` defaults static fonts to `font.weights[0]`, which can be an extreme generated weight rather than a representative 400.

### Required fix

The data model and loader must share one canonical `faces/axes` definition. UI controls should be generated from what is actually loadable, and font readiness should be verified with `document.fonts.load()` / `FontFaceSet.check()`.

# P1 — major workflow and logic defects

## P1.1 — Workbench share URL is not actually portable

Primary file: `src/app/pages/ComparePage.tsx`

The URL stores:

- heading font **index**;
- body font **index**;
- base size;
- ratio.

The actual compared font IDs live in parent state persisted to localStorage. They are not encoded into the shared URL.

Result: a URL copied on one browser/device can open with an empty stack on another browser/device.

Indices also become unstable if the comparison list changes order or an item is removed.

### Required fix

Encode canonical font IDs and role mapping in the URL, e.g.:

`/compare?fonts=inter,source-serif-4&heading=source-serif-4&body=inter&base=16&ratio=1.25`

Validate every query value.

## P1.2 — catalog state is destroyed when opening a font

Primary files:

- `src/app/pages/FontCatalogPage.tsx`
- `src/app/App.tsx`

Filters, sort mode, view mode, visible batch count, font size, tracking, and pangram mode are local state inside `FontCatalogPage`.

The page unmounts when navigating to `/:id`. Returning to `/` creates a fresh catalog state.

There is code in `App.tsx` specifically trying not to scroll to top when returning from a detail page, but the catalog state itself has already been discarded. This creates a contradictory experience: scroll position is treated as persistent while the list configuration is not.

### Required fix

Make catalog state URL-backed (preferred) or lift it to a persistent store. Direct links should reproduce the same catalog query/filter/sort state.

## P1.3 — Back from details always means Catalog, not actual previous context

`FontDetailsPage` receives `onBack={() => navigate("/")}`.

If a user opens a font from Favorites, Back sends them to Catalog rather than Favorites. Context is lost.

Use router history where possible, with a safe catalog fallback for direct-entry URLs.

## P1.4 — active filters can be invisible

`FontCatalogPage` displays active chips only for:

- categories;
- languages;
- variable-only.

But the actual filter model also includes:

- sources;
- minimum weights;
- licenses.

If only a source or minimum-weight filter is active, the top state can still visually read as a neutral `Index`. The clear-filter affordance is also conditionally shown based only on categories/languages/variable.

This makes "why did these results disappear?" unnecessarily difficult to diagnose.

## P1.5 — License filter exists in state and engine but not in UI

`FilterState.licenses` is implemented in `useFontFilter()`, but `FilterPanel` exposes no license controls.

This is dead / incomplete product logic.

Given licensing is a central reason to use an open-font catalog, license filtering should be first-class rather than dormant.

## P1.6 — language filtering hides most supported scripts

The data model can contain Latin, Cyrillic, Japanese, Korean, Chinese, Greek, etc., but the filter UI hard-codes only:

```ts
["Cyrillic", "Latin"]
```

There is also a concrete generator bug: the special CJK branch checks for `sourcePlatform === "Google Fonts / Early Access"`, while `earlyAccessData` is instantiated with source `"Google Fonts"`. Therefore the intended JP/KR/TC script enrichment does not run for those records.

Language/script coverage needs an authoritative source, not string heuristics.

## P1.7 — “Download” usually does not download

Files:

- `FontCard.tsx`
- `FontDetailsPage.tsx`

The Download icon/action opens `font.sourceUrl` in most cases. `Font` even defines `downloadUrl?`, but the UI does not use it.

That is a semantics mismatch. Users should get two explicit actions if both exist:

- `Source / Specimen`;
- `Download`.

Never label a source-page navigation as a direct download.

## P1.8 — “Pairing Algorithm” is mostly deterministic arbitrary selection

`FontDetailsPage` chooses an opposite broad category and then picks a candidate based on a char-code seed from `font.id`.

`ComparePage` suggestion logic similarly picks a candidate from a broad category using an ID-length modulo.

This produces repeatable output, but it is not meaningful typographic pair scoring.

The UI currently names this as an algorithm / suggestion, which overstates what is implemented.

### Required fix

Either relabel it honestly as `Explore contrast` / `Random contrast pair`, or implement a scoring model using metadata such as x-height, width, contrast, optical size, category, proportions, intended use, script coverage, and family compatibility.

## P1.9 — “Related” fonts are not meaningfully related

Font details takes the first six other fonts sharing a broad category. Ordering comes from catalog order, not similarity.

Related should be either removed, explicitly labeled as same-category discovery, or backed by a similarity model.

## P1.10 — Glyph view is not a glyph-coverage inspector

The details page renders a fixed ASCII character string. It does not inspect the loaded font’s actual cmap/glyph coverage and does not show Cyrillic even when the font has a Cyrillic badge.

For a typography research tool, this is a large logical gap.

## P1.11 — automated QA is far below product complexity

`package.json` defines only:

- typecheck;
- build;
- check = typecheck + build.

There is no automated:

- unit testing;
- E2E testing;
- visual regression;
- accessibility testing;
- data schema validation;
- duplicate/provenance validation;
- source URL validation;
- license validation;
- CSS/font asset health validation;
- direct-route test;
- mobile workflow test.

This conflicts with the repository’s own manual contribution checklist, which already asks contributors to verify keyboard use, mobile layout, loading, filters, and direct routes.

## P1.12 — privacy copy and runtime analytics are out of sync

`App.tsx` injects Yandex Metrika immediately, including Webvisor and clickmap.

`PrivacyPage.tsx` only says that anonymized statistics/cookies *may* be collected with internet-statistics services; it does not identify the actual analytics provider or describe the active session/click instrumentation. It also contains generic advertising language unrelated to the current product.

The policy is dated 2025 while this standalone product and its instrumentation changed in 2026.

This requires a proper privacy/compliance review. The technical issue is clear even before legal interpretation: runtime behavior and user-facing disclosure are not maintained from one canonical configuration.

## P1.13 — keyboard accessibility is incomplete across custom interactions

Examples:

- logo is a clickable `div`, not a link/button;
- font names / preview canvases use `div`/`h3` click handlers without keyboard equivalents;
- MarkBuilder grid points are clickable `div`s;
- several icon-only buttons lack accessible names;
- mobile menu trigger lacks robust expanded/control semantics;
- hover-only menus are difficult for keyboard/touch users;
- custom Dialog handles Escape but does not implement a focus trap / focus restoration.

There are some good foundations: skip link, roles in Checkbox/Switch, focus-visible styles, and several aria-labels. The problem is inconsistency.

# P2 — UX / interface quality gaps

## P2.1 — dropdowns depend on CSS hover

Catalog pangram and sort menus are shown through `group-hover:block` rather than explicit open state.

Problems:

- touch interaction is unreliable;
- keyboard opening is incomplete;
- no Escape behavior;
- no focus management;
- user cannot see a persistent expanded state.

Use a real Menu/Popover primitive or implement keyboard/touch semantics explicitly.

## P2.2 — mobile catalog loses important controls

Global size and tracking controls are `hidden md:flex`. The desktop product is a type testing tool; mobile becomes a reduced viewer with fewer comparison controls.

That may be intentional, but it should be an explicit responsive product decision, not just CSS hiding.

## P2.3 — static "pangram" presets ignore the active UI language

All catalog presets are English / code / digits. The default app language is Russian and Cyrillic support is a visible product feature.

Add localized and script-specific specimens, including Cyrillic and mixed-language stress tests.

## P2.4 — sort naming does not match implementation

`sort.styles` / “Most Styles” is implemented by sorting on `font.weights.length`, not `font.styles.length`.

This should be corrected or renamed to weight count.

The default “Curated” rank is simply the current array order; if it is meant to be curated, the dataset should have an explicit stable ranking field and rationale.

## P2.5 — empty-state copy is contextually wrong

When no font matches a search/filter, the empty state shows `filters.platform.note` (library is updating / more platforms coming soon). That message does not explain a failed search or restrictive filters.

## P2.6 — “Other” source checkbox has no indeterminate state

It is considered checked if at least one low-volume source is selected. Clicking it in a partial state deselects all low-volume sources.

A tri-state/indeterminate checkbox or expandable source group would be clearer.

## P2.7 — source taxonomy is semantically mixed

The UI calls the dimension `Platform`, but `font.source` can mean:

- Google Fonts;
- a foundry;
- GitHub;
- an organization;
- an editorial bucket such as `Uncut / Indie`;
- a technology / project label.

Separate at least:

- provider/distribution platform;
- foundry/designer;
- collection/editorial source.

## P2.8 — favorites are device-local only

Favorites use localStorage. This is a good zero-auth baseline but offers no:

- export/import;
- share link;
- JSON backup;
- multi-device sync.

A lightweight export/import feature would solve most of this without adding accounts.

## P2.9 — favorites load every saved family immediately

`FavoritesPage` passes the entire saved collection into `FontLoader`. A large collection can create a large burst of external CSS/font requests.

Use viewport-based or chunked family loading.

## P2.10 — catalog loader never exposes font readiness

A stylesheet can fail and be removed, but the card remains visually valid using a fallback stack. There is no distinction between:

- loading;
- loaded;
- fallback;
- failed;
- unavailable.

For a font comparison tool this state should be explicit.

## P2.11 — already loaded external styles accumulate indefinitely

The global loader keeps successful stylesheet links for the session. Browsing many families can grow the document head and resource/memory footprint continuously.

A cache is useful, but it should have a deliberate lifecycle / budget.

## P2.12 — filter/source checkboxes use very small physical targets

Several controls are visually around 12–16 px. Even if labels are clickable, the interaction system should standardize a larger hit area while preserving the minimal visual shape.

## P2.13 — Workbench ignores its own `previewText` API

`CompareProps` defines `previewText` and `setPreviewText`, and App passes them, but `ComparePage` destructuring ignores both and uses separate `customContent` state.

That is a clear state/API mismatch. Preview text should either flow through the product or the unused props should be removed.

## P2.14 — Workbench numeric inputs are not validated

URL and number inputs accept arbitrary `Number(...)` values for base size, ratio, and font indices.

Malformed query parameters or user input can produce invalid state. Add schemas / bounds / safe defaults.

## P2.15 — Workbench export is incomplete

Generated Tailwind config assigns fonts but does not include loading/import instructions. It also uses `sans-serif` fallback for display regardless of whether the chosen display family is serif or monospaced.

Export should produce a self-contained integration recipe for each source type.

## P2.16 — font code snippets are source-label dependent rather than loader-capability dependent

The details page only emits a Google import if `font.source === "Google Fonts"`. Several families are intentionally loaded from Google despite being editorially labeled Adobe / Canonical / Rsms / etc.

The code/export system should consume a canonical webfont source definition, not infer behavior from a marketing source label.

## P2.17 — related-detail cards are display-only

Related cards have no navigation action. They occupy product space without completing the discovery loop.

## P2.18 — sticky layout relies on magic pixel offsets

Examples include `top-[152px]`, `pt-[137px]`, and multiple assumptions about a 64px header.

This is brittle when:

- copy wraps;
- browser zoom changes;
- localization changes dimensions;
- header design changes.

Centralize shell dimensions as CSS variables or avoid stacked manual offsets.

# Localization and content audit

## Default language and document language disagree

`LanguageProvider` defaults to Russian when no preference is saved, while `index.html` permanently declares:

```html
<html lang="en">
```

`document.documentElement.lang` is never synchronized with the active language.

This affects accessibility and language-aware browser/search behavior.

## Russian copy contains unfinished / inconsistent terms

Examples in the current translation file include:

- `filters.other = "Other"`;
- `share = "Шер"`;
- `compare.ratio = "Ратио"`;
- `Уровень-H`, `Уровень-P`;
- `КЭШ`, `ЮНИТОВ`;
- a mix of natural Russian, transliteration, English system language, and cyber-industrial stylization.

A stylized voice is fine, but it needs a deliberate vocabulary system. Right now some terms look intentional while others look simply unfinished.

## Legal pages are not actually bilingual

Privacy / Terms / License use the language state only for the Back label. Their substantive headings/body are hard-coded Russian.

English UI therefore leads to Russian-only legal content.

## Error UI is English-only

`ErrorBoundary` displays English hard-coded copy regardless of selected language.

It also says “This has been logged”, but the implementation only calls `console.error`. That statement should be removed unless real telemetry exists.

# Accessibility audit

## Positive foundations

- skip-to-content link exists;
- Checkbox and Switch expose `role` + `aria-checked`;
- many icon actions have aria-labels;
- visible focus styles exist in several primitives;
- Protocol TOC has an aria-label and current-state signal.

## Missing foundations

1. interactive `div`/`h3` elements should be links/buttons;
2. icon-only controls need consistent names;
3. mobile drawer needs focus trapping, Escape support, initial focus, and focus restoration;
4. Dialog needs focus management, not only Escape + body scroll lock;
5. tabs on Font Details should use tab semantics (`role=tablist/tab/tabpanel`, `aria-selected`);
6. hover menus need keyboard/touch behavior;
7. custom drawing grid needs keyboard operation or an accessible alternative;
8. controls need larger hit targets;
9. animation-heavy pages should honor `prefers-reduced-motion`;
10. the active page should use `aria-current` in primary navigation.

# Dark / invert mode audit

The app already contains a complete `.dark` token set, but the actual UI toggle does not use it. Instead it applies:

```css
html.invert-mode {
  filter: invert(1) hue-rotate(180deg) brightness(0.9);
}
```

This is a visual inversion hack, not a real dark theme.

Problems:

- page-wide filter can create a large compositing layer;
- color meaning can change unexpectedly;
- photos/videos require manual re-inversion;
- shadows/borders/overlays can look wrong;
- browser `color-scheme` remains `light`;
- `theme-color` remains light;
- mode is not persisted;
- system preference is ignored;
- there is already dead dark-token infrastructure that is not connected to the toggle.

Recommendation: implement actual theme tokens/classes and delete invert-mode once parity is reached.

# Performance / runtime audit

## Font loading is the dominant risk

External CSS comes from several independent providers. The current architecture can create many stylesheet requests and then many font-file requests as the user scrolls.

Needed improvements:

- per-family resource registry;
- content-addressed cache keys;
- requested-face minimization;
- viewport-aware loading;
- `document.fonts` readiness checks;
- failure states;
- timeouts/retry policy;
- provider health/fallback strategy;
- optional connection hints for dominant providers.

## About / Protocol animation budget

About performs mouse-distance calculations and state updates for multiple kinetic characters, uses variable/slant animation assumptions, and includes continuous marquee / Motion effects.

Protocol contains many lazy interactive modules and sticky sections.

Both need:

- reduced-motion mode;
- mobile animation budget;
- verification under low-power devices;
- avoiding page-wide filter-based dark mode during heavy animation.

## Kinetic variable behavior is not guaranteed across system fonts

About applies `fontVariationSettings` (`wght`, `slnt`) to text without pinning the effect to a known font supporting those axes. Behavior can therefore vary by OS/browser/font fallback.

Use a known bundled/loaded variable family for demonstrations.

## MarkBuilder timers are not centrally cancelled

Glyph generation creates multiple `setTimeout` callbacks. The effect’s initial delayed generation also creates a timeout. These should be tracked and cancelled on unmount / subsequent generation to avoid stale animation writes.

# SEO / routing / social audit

## Static HTML metadata only describes the generic home page

`index.html` contains one English title/description/OG description. Runtime changes only `document.title`.

Missing or incomplete:

- canonical URL;
- route-specific descriptions;
- route-specific OG metadata;
- `og:url`;
- social preview image;
- structured data;
- sitemap;
- per-font indexable metadata.

## GitHub Pages SPA fallback is functional but weak for deep-route SEO

The deploy copies `index.html` to `404.html` so BrowserRouter deep routes can hydrate. This is acceptable for human navigation, but a direct deep route is still reached through GitHub Pages’ not-found mechanism before React takes over.

For a catalog where every typeface should be a discoverable page, pre-rendered/static family pages would be substantially stronger.

## Document language is static

`lang="en"` conflicts with the default Russian runtime language and never changes.

## Favicon is injected only after JS starts

This works for the app, but favicon / canonical basic metadata should be present in the HTML shell where possible.

# Deployment / CI audit

The site is working, but the current workflow still contains temporary recovery/debug mechanics added while GitHub Pages was stuck.

Current flow:

1. build `dist`;
2. force-push `dist` to `gh-pages`;
3. manually POST a Pages build request;
4. fetch Pages diagnostics;
5. write diagnostics into the public `dist` content;
6. make another commit and force-push `gh-pages` again.

Problems:

- operational diagnostics become public site files;
- deployment branch is force-pushed twice per main build;
- recovery instrumentation becomes permanent production behavior;
- `|| true` around API requests can hide failed control-plane calls;
- the second push makes reasoning about deployment source SHA harder.

Now that Pages is operational, simplify the workflow and keep diagnostics as Action logs/artifacts rather than public web files.

Longer term, prefer the official Pages artifact/deploy action path if the repository/account setup is stable with it.

# Architecture / maintainability audit

## `mockFonts.ts` is simultaneously schema, generator, registry, heuristics, and product content

This is too many responsibilities in one source file.

Split into:

- schema/types;
- authoritative provider adapters;
- source manifests;
- generated normalized dataset;
- validation report;
- runtime read-only catalog.

The runtime should never execute catalog-construction heuristics.

## Source semantics are overloaded

`source` is used for filtering, display labels, URL behavior, and loader routing. These are different concepts and should be separate typed fields.

## Runtime behavior relies on `window` APIs directly in product state

Workbench directly calls `window.history.replaceState` instead of router search-param APIs. This bypasses normal router state semantics.

## Weak typing remains in route wrapper

`FontDetailsWrapper` uses `[key: string]: any` for the majority of its props. Define an explicit interface.

## Duplicate utilities / migration leftovers

There are two `cn` utility locations (`components/ui/utils.ts` and `lib/utils.ts`) plus a large design-token surface inherited from the previous UI stack. Consolidate once the component inventory is stable.

## Dead / incomplete model fields

Examples:

- `downloadUrl?` exists but is not used correctly;
- `licenses` filtering exists but has no UI;
- Workbench preview props exist but are ignored;
- `.dark` theme exists but is not used by the theme toggle.

Dead partial features create false complexity.

# Product positioning gaps

The strongest future version of ONOD Fonts should not be “a prettier Google Fonts list”. It already has the beginnings of something more useful: **a typography research and decision environment**.

To make that proposition real, the next version should center on five truths:

### 1. Every displayed fact is traceable

A designer should be able to see where script support, license, weights, axes, foundry, and download information came from.

### 2. Every specimen is known to be rendering the requested family

Fallback should never be silent.

### 3. Comparison state is portable

A colleague should be able to open one URL and see exactly the same families, roles, specimen text, size system, and settings.

### 4. Pairing should be explainable

If ONOD recommends a pair, show why: category contrast, proportions, x-height, stroke contrast, tone, script compatibility, intended role, etc.

### 5. The catalog should be a tool, not a database dump

High-value workflows:

- shortlist;
- compare;
- test in real UI/editorial contexts;
- inspect scripts/glyphs;
- inspect variable axes;
- verify license/source;
- export integration code;
- share the decision.

# Recommended target architecture

## A. Build-time catalog pipeline

Provider adapters ingest official metadata where available and output a normalized `catalog.generated.json` plus a validation report.

Build should fail for records marked `verified` if required facts are missing or inconsistent.

## B. Provenance layer

Every external fact stores source URL + last verification time. UI can distinguish:

- Verified;
- Derived;
- Unknown;
- Unavailable.

## C. Font runtime registry

One central loader owns:

- provider-specific CSS URLs;
- family/face/axis requests;
- loading promises;
- cache keys;
- readiness verification;
- errors;
- retries;
- optional eviction.

Components consume status; components do not construct CDN URLs independently.

## D. URL-first workspace state

Catalog query/filter/sort/view and Workbench selections should have canonical URL representations. localStorage can persist convenience defaults but must not be the only source for shareable work.

## E. Test matrix

Minimum automated gate:

1. schema/data validation;
2. unit tests for filters/ranking/url codecs;
3. Playwright smoke flow: catalog → filter → detail → back → compare → share;
4. direct route smoke tests under production base path;
5. axe accessibility checks for primary pages;
6. mobile viewport smoke tests;
7. font loader tests with successful and failed providers;
8. link/source health checks on a scheduled workflow.

# Definition of a trustworthy v1

ONOD Fonts can be treated as a trustworthy production catalog when all of these are true:

- no visible metadata is fabricated without a derived/unknown label;
- every specimen knows whether the requested font actually loaded;
- displayed weights/axes correspond to real available faces;
- license/source information has provenance;
- filtering operates on canonical fields;
- a shared Workbench URL reproduces the exact comparison on another device;
- opening a detail and going back preserves the user’s workspace;
- all primary workflows are keyboard accessible;
- mobile has an intentional feature model rather than hidden desktop controls;
- CI validates data + behavior + accessibility, not only compilation;
- deployment no longer carries temporary public diagnostics;
- deep font pages have a deliberate SEO/indexing strategy.

## Final assessment

The current project is a **strong prototype / early product with a credible visual language**, but not yet a trustworthy typography reference system.

The biggest mistake would be to spend the next cycle adding another thousand fonts or decorative interface modules. The correct next cycle is to turn the existing surface into a **verified, observable, shareable typography engine**.

Once data provenance + loading fidelity + URL-state + QA are repaired, the existing Catalog / Details / Workbench / Protocol structure becomes a genuinely strong base for a much larger ONOD typography product.
